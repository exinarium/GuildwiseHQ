### DevOps and repository hygiene
The DevOps engineer and Ask DevOps, approvals, conflicts, repository hygiene and saved work, the toolchain, the working branch and new repositories.
- The DevOps engineer: You get one DevOps engineer per workstation automatically. It cannot be fired, only reset (which clears its sandbox but keeps it assigned). It does not take cards from the queue.
- The DevOps command log: Every command a DevOps shift ran is logged. The workstation owner sees all of them on that workstation's log page, the organization Owner sees those of the organization's shifts on Organization > DevOps commands, and the platform sees counts only.
- The DevOps queue: Requests are served in this order: first those somebody is waiting on (a card parked on the request, an agent still working on that card, or a card held at Test deploy), then any request older than 30 minutes, then the rest by arrival. One engineer runs one request at a time;…
- When two branches conflict: Conflict work now happens inside the safety box, in a copy of the repository the runner makes for it; when DevOps reports Resolved:, the runner itself moves the real branch forward, and only onto a conflict it saw.
- Repository hygiene: Once a day per workstation by default, the runner tidies the repositories on that machine. It is a fixed routine, not an AI: with "Tidy the code folders every day" ticked on the computer it runs without asking you; otherwise each run waits for your yes.…
- New repositories and the toolchain: When you add a repository in Project settings, Repositories, the DevOps engineer of each workstation of the project puts it there. Pick An existing repository and it is cloned into the workstation's first repository folder (guildwise-runner repos add);…
- Fix with DevOps: Next to every item that failed or is missing there is a Fix button: a tool of the Development environment (missing, failed or needs access), a ticked right on the Workstations page that failed Verify now, and a repository under Repositories that failed to clone.…
- Rights: A ticked right is checked on the machine itself. On the Workstations page each ticked right shows verified or failed with the reason and how to fix it (for Docker: run the installer again so the runner gets its own rootless Docker;…
- The working branch: The working branch is where finished work is combined: the repository's default branch (usually main) unless you name another such as develop, which is created from the main branch (where pull requests go; default: the repository's default branch) and pushed when it does not exist.…
