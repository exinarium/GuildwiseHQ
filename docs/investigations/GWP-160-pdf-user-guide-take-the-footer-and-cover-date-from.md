# GWP-160: PDF user guide takes its footer and cover date (and edition) from the release

## Question

`docs/guide/build-guide.mjs` hard-codes the footer date `7 October 2026` and `docs/guide/parts/cover.html` hard-codes
the cover date. When release docs prep ('Update user guide') rebuilds the PDF, the PDF shows a stale date. How should
the build take one date (and an optional edition) from a single source, and how does release prep pass the date and
version of the release it prepares?

### What the release "knows" when docs prep runs

- The release date is set **at approval**: `startReleaseShipIn` (`apps/server/src/release/ship.ts:162`) takes
  `ctx.clock.now()` as the ship date and stores it in `release_ships.release_date`.
- Docs prep is a gate **before** approval: `startReleaseDocsPrep` refuses with `release_shipping` when any proposal of
  the project is approved (`apps/server/src/release/docs-prep.ts:231-239`).
- So while docs prep runs, the release being prepared normally **has no date yet**. The card foresaw this ("unless the
  release has no date ... use the date the prep runs and say so in the step output"). In practice the run date is what
  will be used, and the output says so every time. The design still reads a release date first, so the rule stays right
  if a release ever carries a date before prep.
- The version: a live proposal for the repository (`release_proposals.state IN ('proposed','approved')`) carries
  `recommended_version` and, after approval, `version`. The repository's release branch (`payload.releaseBranch`, for
  example `release/1.6.0`) names it as well. The runner's `release-facts.ts` `lastReleaseTagAt` is the **last** tag, not
  the release being prepared, so it is not a source.
- The "date the prep runs" is best taken from the server's `release_docs_prep_runs.started_at`, not from the runner's
  clock: it is one value for the whole run (stable across step retries and repositories) and is not "the wall clock of
  the build machine".

### Release branches cut before this change

Release prep runs the repository's **own** scripts from the release branch worktree. A branch cut before this card
merges (release/1.6.0 itself) has the old `build-guide.mjs`, which ignores unknown arguments: passing `--date` would not
fail, but the PDF would still show `7 October 2026` while the step output claims another date. The step must therefore
check that the script supports the flags before it passes them and claims the date.

## Options

### A. Argument form

| Option | For | Against |
|---|---|---|
| **CLI flags `--date <YYYY-MM-DD>` `--edition <text>` (recommended)** | same form as the existing `--out`; visible in the runner's exec call and in tests; easy to detect in the script text | none relevant |
| Environment variables `GUIDE_DATE`/`GUIDE_EDITION` | no argv parsing | invisible in logs and the exec call; harder to test the runner call; leaks into child processes |
| Both | flexible | two ways to say one thing; the card asks the Architect to pick one |

### B. Single source for footer and cover

| Option | For | Against |
|---|---|---|
| `assemble-guide.mjs` fills the cover, `build-guide.mjs` fills the footer | cover text in guide.html | two scripts need the same flags; release prep and people must pass them twice; they can disagree, which breaks the constraint |
| **`build-guide.mjs` fills both (recommended)**: cover.html carries empty placeholder elements, build-guide sets them in the loaded page before the first render, and uses the same value in the footer template | one script, one parsed value, footer and cover cannot disagree; assemble unchanged; guide.html no longer churns with the date | guide.html opened on its own shows an empty Date cell (it is a generated build input, "do not edit") |
| String-replace placeholders in the HTML and `page.setContent` | testable without Chromium | relative `assets/...` URLs need the file base URL; setContent/about:blank base handling is fragile with `file://` images |

### C. Edition placement

| Option | For | Against |
|---|---|---|
| Put the version into the existing Edition row | no new row | the row is a long description ("Guide 2.0, written for ..."); mixing a version into it reads badly and changes that text |
| **A new cover row `Release` above `Edition`, present only when an edition is given (recommended)** | without the flag the cover is exactly as today (the row is removed before rendering); clear label | one more row on the cover when the flag is given |
| In the footer as well | visible on every page | changes the footer layout; not asked for |

### D. Release date and version source

| Option | For | Against |
|---|---|---|
| Runner works it out (branch name, its own clock) | no server change | runner clock is "the build machine's wall clock"; differs per repository and per retry |
| **Server resolves in the guide step hook and sends it in `stepInput.release` (recommended)** | uses the release facts the server has (proposal version, ship date, run start); one value per run | small shared-schema and server change |

## Recommendation

A1 + B2 + C2 + D2. Details follow.

## Design

### 1. `docs/guide/guide-meta.mjs` (new, plain ESM, no dependencies)

Pure helpers, importable without Playwright, so they can be unit-tested and so `build-guide.mjs` can validate its
arguments **before** it loads Playwright or launches Chromium.

```js
export const DEFAULT_GUIDE_DATE = '2026-10-07'; // renders as "7 October 2026", today's date
const MONTHS = ['January', 'February', 'March', 'April', 'May', 'June', 'July', 'August', 'September', 'October', 'November', 'December'];

export class GuideArgError extends Error {}

/** "2026-11-08" -> "8 November 2026"; throws GuideArgError naming the value when it is not a real calendar date. */
export function longDate(iso) {
  const m = /^(\d{4})-(\d{2})-(\d{2})$/.exec(String(iso));
  if (!m) throw new GuideArgError(`--date "${iso}" is not a date in the form YYYY-MM-DD`);
  const [y, mo, d] = [Number(m[1]), Number(m[2]), Number(m[3])];
  const t = new Date(Date.UTC(y, mo - 1, d));
  if (t.getUTCFullYear() !== y || t.getUTCMonth() !== mo - 1 || t.getUTCDate() !== d)
    throw new GuideArgError(`--date "${iso}" is not a real calendar date`);
  return `${d} ${MONTHS[mo - 1]} ${y}`;
}

/** argv (process.argv.slice(2)) -> { out, date, dateText, edition }. Throws GuideArgError on a bad or missing value. */
export function parseGuideArgs(argv) { /* see rules below */ }

/** The Chromium footer template for a date text (escaped). */
export function footerTemplate(dateText) { /* today's template with ${dateText} in place of the literal */ }
```

Rules for `parseGuideArgs`:

- Flags: `--out <file>` (as today), `--date <YYYY-MM-DD>`, `--edition <text>`. Space form only, like `--out`.
- A flag with no value, or whose value starts with `--`, is an error naming the flag.
- `--date` absent: `date = DEFAULT_GUIDE_DATE`. Present: validated by `longDate` (rejects `not-a-date`, `2026-13-40`,
  `2026-02-30`, `2026-1-5`).
- `--edition` absent: `edition = null`. Present: trimmed, 1 to 40 characters, no control characters
  (`/^[^\u0000-\u001f\u007f]{1,40}$/`), else an error naming the value. It is written with `textContent`, so no HTML
  escaping is needed on the cover.
- Unknown arguments stay ignored, as today.
- No `Intl`/ICU: the month table keeps the output identical on any Node build (no new dependency, constraint met).

### 2. `docs/guide/parts/cover.html`

Replace the Date row and add the Release row (no hard-coded date remains):

```html
<tr><td>Date</td><td><b data-guide-date></b></td></tr>
<tr data-guide-release><td>Release</td><td><b data-guide-edition></b></td></tr>
<tr><td>Edition</td><td>Guide 2.0, written for ... (unchanged)</td></tr>
```

### 3. `docs/guide/build-guide.mjs`

1. At the very top (before `e2eRequire`), parse the arguments:
   ```js
   let meta;
   try { meta = parseGuideArgs(process.argv.slice(2)); }
   catch (e) { if (e instanceof GuideArgError) { console.error(`build-guide: ${e.message}`); process.exit(2); } throw e; }
   ```
   A bad value therefore exits non-zero before any browser starts, and no PDF is written (AC 4).
2. `const footer = footerTemplate(meta.dateText);`.
3. After `page.goto(...)` and `document.fonts.ready`, **before** reading the TOC entries and the first render, fill the
   cover:
   ```js
   const filled = await page.evaluate(({ dateText, edition }) => {
     const dates = [...document.querySelectorAll('[data-guide-date]')];
     for (const el of dates) el.textContent = dateText;
     const row = document.querySelector('[data-guide-release]');
     if (row) {
       if (edition) row.querySelector('[data-guide-edition]').textContent = edition;
       else row.remove();
     }
     return { dates: dates.length, release: Boolean(row) };
   }, meta);
   ```
   - `filled.dates === 0` and `--date` or `--edition` was given: fail with
     `guide.html has no date placeholder; run node docs/guide/assemble-guide.mjs first` (exit 1, no PDF).
   - `filled.dates === 0` and no flag was given: carry on (an old guide.html with the literal date still builds as
     before; backwards compatible).
   - `--edition` given and no `data-guide-release` row: same failure as above.
4. After the last pass, before `fs.writeFileSync(OUT, pdf)`: check the final page texts (keep the last `texts` outside
   the loop) with whitespace squashed: every page contains `meta.dateText` (the footer), and, when an edition is given,
   page 1 contains it. If not, throw `the PDF does not show <dateText> on page <n>` and write nothing. This turns AC 2
   into a self-check of every build. If the cover page's footer text turns out not to be extracted by pdf-parse,
   relax the check to "every page from 2" and say so in the handoff; do not drop it silently.
5. Update the header comment: `Usage: node docs/guide/build-guide.mjs [--out <file.pdf>] [--date YYYY-MM-DD] [--edition <text>]`.

### 4. `docs/guide/guide.html`, `docs/guide/Guildwise-HQ-User-Guide.pdf`

Do not commit a regenerated `guide.html` or PDF (as ruled for GWP-11, ledger 21fb83d0 / c80bf75f). Release prep and the
README flow always run `assemble-guide.mjs` first, which copies the new cover. With an old `guide.html`, a build without
flags still works (rule 3.3).

If you run `assemble-guide.mjs` while testing, check that `git diff docs/USER-GUIDE.md` is empty (it rewrites the
contents block; it must be a no-op) and then `git checkout -- docs/guide/guide.html docs/USER-GUIDE.md docs/guide/*.pdf`.

### 5. Shared schema: `packages/shared/src/release/user-guide.ts`

Input (built by the server):

```ts
const IsoDate = z.string().regex(/^\d{4}-\d{2}-\d{2}$/);
export const ReleaseDocsPrepGuideInputSchema = z.object({
  guidePath: ..., coveredSources: ..., denyList: ...,   // unchanged
  /** The release being prepared, for the PDF guide's cover and footer. Absent from an older server. */
  release: z.object({
    version: z.string().min(1).max(40).nullable().default(null),
    /** The release's own date; null until the release is approved (normal during prep). */
    date: IsoDate.nullable().default(null),
    /** The day the prep run started (server clock, UTC): the fallback. */
    runDate: IsoDate,
  }).optional(),
});
```

Output (add, all optional so stored outputs still parse):

```ts
pdfDate: IsoDate.optional(),                         // the date passed to the build
pdfDateSource: z.enum(['release', 'run']).optional(),
pdfEdition: z.string().max(40).optional(),
```

Also add a pure helper there (or in `tags.ts`): `releaseVersionFromBranch(branch)`:
`/^release[/-]v?(\d+\.\d+(?:\.\d+)?(?:-[0-9A-Za-z.-]+)?)$/` -> the version, else null. Unit-test it in the shared suite.

### 6. Server: `apps/server/src/release/docs-prep-steps.ts`

Extend the `guide` hook's `stepInput` (the `repo` row is `release_docs_prep_repos` joined with `project_repos`; it has
`repo_id` and `branch`; `run` has `started_at`):

```ts
release: await guideRelease(db, run, repo),

export async function guideRelease(db: Queryable, run: Row, repo: Row) {
  const p = await one(db,
    `SELECT COALESCE(version, recommended_version) AS v FROM release_proposals
      WHERE repo_id=$1 AND state IN ('proposed','approved') ORDER BY updated_at DESC LIMIT 1`, [repo.repo_id]);
  const version: string | null = p?.v ?? releaseVersionFromBranch(repo.branch);
  const ship = version
    ? await one(db, `SELECT release_date FROM release_ships WHERE repo_id=$1 AND version=$2 AND status <> 'failed'`,
        [repo.repo_id, version])
    : null;
  return { version, date: ship ? isoDay(ship.release_date) : null, runDate: isoDay(run.started_at) };
}
```

`isoDay`: `release_date` is a Postgres `date` and `started_at` a `timestamptz`; `pool.ts` sets no parser for type
1082, so both arrive as JS `Date`. Format a `date` column with local-time getters (pg builds it at local midnight) and
`started_at` with `toISOString().slice(0, 10)` (UTC, the same rule as the ship date in `ship.ts:162`). Comment in code
that `date` is normally null during prep because the release gets its date at approval.

### 7. Runner: `apps/runner/src/git/release-docs-prep-guide.ts`

Add a pure exported helper and use it where the build step is assembled (lines 304-311):

```ts
/** What the PDF build gets: the release date (else the run date, else today on this runner) and the version. */
export function guidePdfMeta(release: ReleaseDocsPrepGuideInput['release'], now: Date) {
  const date = release?.date ?? release?.runDate ?? now.toISOString().slice(0, 10);
  const source: 'release' | 'run' = release?.date ? 'release' : 'run';
  return { date, source, edition: release?.version ?? null };
}
```

In `runGuideStep`, inside the `else` branch that builds the PDF:

- Read the build script text once (`readFileSync(join(wt, build), 'utf8')`). Pass `--date <date>` only if it contains
  `'--date'`, and `--edition <version>` only if it contains `'--edition'` and an edition exists.
- Script without `--date` support (a release branch cut before this change): pass nothing, leave `pdfDate` unset and
  add a warning `the PDF build script takes no --date, so the PDF keeps the date written in it`.
- Otherwise set `out.pdfDate`, `out.pdfDateSource`, `out.pdfEdition` (when passed). When the source is `run`, add a
  note `the release has no date yet, so the PDF shows the day this prep run started (<date>)`. When `release` was
  absent from the input (older server), the note says `today on this workstation` instead.
- Set them only on the path that actually ran the build (`out.pdf = 'rebuilt'`), never on `no change` / `no PDF build`.
- Use `new Date()` for `now` in the step; tests call `guidePdfMeta` with a fixed date.

The build call becomes `['node', [build, ...dateArgs, ...editionArgs], 10 * 60_000]`. Argument values go through
`ctx.exec` as an argv array (no shell), so the version string cannot inject anything.

`release-docs-prep-steps.ts` needs no change (the handler is already registered).

### 9. `docs/guide/README.md`

In "Rebuild the PDF from the existing pictures", add a short subsection "Date and release on the cover":

- `--date YYYY-MM-DD` sets the date in the footer of every page and on the cover (one value; rendered as
  `8 November 2026`). Default: `2026-10-07` (`7 October 2026`).
- `--edition <text>` adds a `Release` row with that text to the cover. Without it the cover has no such row.
- An invalid date stops the build with an error naming the value; no PDF is written.
- The values are filled in by `build-guide.mjs`; `parts/cover.html` holds only the placeholders
  (`data-guide-date`, `data-guide-release`, `data-guide-edition`), so run `assemble-guide.mjs` after changing it.
- Release prep ('Update user guide') passes `--date` with the release date, or the day the prep run started when the
  release has no date yet (normal before approval), and `--edition` with the release version; the step output shows
  which date was used.
- Update the layout table row of `parts/cover.html` and `build-guide.mjs` accordingly, and add `guide-meta.mjs`.

## Risks and traps

- **The release has no date during prep.** By design of the gate, `pdfDateSource` will almost always be `run`. This is
  the card's documented fallback, not a bug. If the owner later wants the approval date in the PDF, the ship step would
  have to rebuild the PDF after approval; that is a separate change.
- **Old release branches.** Without the support check the output would claim a date the PDF does not show (section 7).
- **guide.html and PDF churn.** Do not commit regenerated build outputs (section 4).
- **Group overlap with GWP-161** (per-repository guide path): it touches the same `ReleaseDocsPrepGuideInputSchema`,
  the server `guide` hook and `runGuideStep`. Keep the new `release` field separate from `guidePath` so the two cards
  merge cleanly; whichever lands second rebases on the other's schema.
- **Timezone.** `runDate` is a UTC day (as the ship date). A run started just after midnight local time may show the
  previous or next day; acceptable and consistent with the release commit date.
- Edition text is user-chosen (a proposal version); it is passed as an argv element and written with `textContent`,
  so there is no shell or HTML injection.

## Out of scope

- Per-repository guide path setting (GWP-161).
- Any change to `docs/USER-GUIDE.md` content or the PDF layout beyond the Date and Release rows.
