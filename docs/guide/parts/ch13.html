TOCMARK_s13x1_13.1 Decisions that shape the product

This table lists the most important architectural decisions from docs/ARCHITECTURE.md section 24 ("Resolved ambiguities and defaults"), which lists 22 decisions; all are shown here with the numbers used there.

#Decision
1One organization per user; agent names are unique per organization forever (including retired agents).
2Card owner = the user who created or imported the card.
3Rework and Blocked are not stages. Rework is the build stage with rework_round > 0 (or a bug card); Blocked is a status overlay; board columns are derived.
4Test failure before finalize creates a bug child card on the code-bugfix workflow that shares the parent's worktree and branch and goes to the original builder first; the parent waits in Test until the child passes review, then re-enters the Test queue.
5Post-finalize failures and regression bugs create standalone bug cards in Spec for the BA (M4) and never block merges.
6Dependencies gate the first build claim until every dependency is done (finalized); dependent cards still branch from the working branch. Branching from a dependency's branch is out of scope for v1.
7Card pinning to a workstation: after the first claim creates the worktree, all later stages run on that workstation. Cards do not move between workstations; the manager can re-home a card, which restarts its current stage from the base branch.
8Offline timeout is implemented as a 1-hour lease refreshed by 15 s heartbeats.
9Large-tier review = two approvals from two distinct senior reviewers, sequentially.
10Instructions are written to the agent's own CLAUDE_CONFIG_DIR/CLAUDE.md, not the worktree's CLAUDE.md (which belongs to the repo and must not be modified or committed).
11Agent reporting uses the aom CLI over a localhost IPC with a per-shift token; fenced aom-report JSON in the final message is a fallback.
12Provider credentials stay in the runner's local config (CLAUDE_CODE_OAUTH_TOKEN / ANTHROPIC_API_KEY) or are linked from the user's default Claude config; never sent to the site.
13Vault sync, rebases, worktree management and completion actions are deterministic runner code; LLM DevOps shifts handle only ad-hoc requests.
14Decision files and taste rules reach the vault through vault.write runner commands, since the site holds no vault content.
15Escalation chain (M7 replaced the M2 default of going straight to the desk): a question goes to the card's previous holder or a senior agent of the asker's role (an online agent only), then to the BA, then to the manager's desk. A question nobody takes within 10 minutes moves on by itself; without a peer or BA it goes straight to the desk.
16DevOps engineer is auto-hired per (user, workstation) at pairing (it cannot be fired, only reset: docs/SPEC.md, Operating model).
17Project sharing requires the invitee to accept (pending until then).
18Scheduled overflow is limited to one extra shift per organization at a time.
19Research and feed roles (researcher, checker, scout, curator) ship as built-in roles.
20Operational, non-event state: auth sessions, heartbeats and lease refresh, connection flags, shift progress tails, runner inbox and command queue.
21Risk tier is computed by the runner at build handoff: ≥ 200 changed lines, any architectural glob, or refactor ⇒ large.
22Finalize before the BA exists (M4–M6): the manager triggers it from the card. From M7 the BA claims the Finalize stage and reports aom finalize --action ...; the runner executes the completion action (pr, push_branch or merge; large merges wait for desk approval), and the manager's Finalize button remains as an override.

TOCMARK_s13x2_13.2 Known limitations

LimitationEffectWorkaround
Single server instance for v1No horizontal scaling; one VPS instance only.Size the VPS for it; v1 has no clustering. Event store appends use a global lock (see docs/DEPLOY.md).
Point-in-time recovery not builtDatabase backups are snapshots, not transaction logs.Set up automated VPS snapshots (daily). Restore from the most recent backup if needed.
No agent-to-agent blocking (intentional)Agents never wait on another; work always flows forward or is explicitly blocked by a manager question.By design: reduces queuing and communicates blockers to the manager explicitly.
Agents run only on user workstationsAgents cannot run on the server or on shared CI infrastructure (v1 scoping).Pair a dedicated low-power machine as a workstation if you need always-on agents.
No cost tracking per agent or projectNo token accounting or cost forecasting (v1 scope).Use the HR board and metrics for token counts per agent; check cost with your provider.
Vault URLs may not carry credentialsA URL with a password or token is refused when you register or edit a vaultUse SSH keys or a git credential helper on the workstation
No native Windows sandboxWindows requires WSL2; unsandboxed native Windows is an explicit opt-in only.Use WSL2 (recommended); see docs/RUNNER.md for setup.
No agent pool or autoscalingYou must hire agents manually and manage capacity.The HR board recommends hiring, and a desk alert fires when testers are busy while E2E work waits.
A resumed shift re-runs the agent from the startAfter a runner restart within the 1-hour lease the shift keeps its id and worktree, but the agent process is restarted, not re-attached (Claude starts a fresh run on the card branch).Expect repeated work after a runner crash; keep the runner under systemd/launchd so restarts are quick.
Jira resolution posts a comment onlyA resolution update is posted as a comment; the ticket is not transitioned (transitions are workflow specific).Move the ticket yourself after approving the update.
Definition files are not published retroactivelyA definition file is written to the vault when a role or workflow version is approved (without a vault only the site copy exists); a vault added later does not receive earlier approved definitions.Copy the YAML files into the vault by hand, or approve new versions after the vault exists.
A manually finalized card gets no BA-drafted ticket updateThe BA drafts the outbound update in its Finalize shift; if you finalize the card yourself that shift never runs.Write the outbound update yourself from the card (the manager can write a draft).
No model advice for other modelsThe HR board recommends model changes only along the ladder haiku, sonnet, opus; models outside it get no advice.Change such an agent's model by hand.
Real Claude Code only run on LinuxThe real adapter was exercised on Linux only. WSL2 uses the same sandbox (bubblewrap and socat); macOS (Seatbelt) and native Windows were not tested with real Claude Code.On macOS, run aom-runner doctor and a small card first. On Windows use WSL2.
MSW dev mocks are partialThe web app can run against MSW mocks (VITE_MSW=1), but they cover only part of the API.Use the real server for anything beyond basic screens.
Biome reports lint warningspnpm lint finishes with warnings (about 690) and no errors.None needed; the check passes.
Limited shifts per workstation at onceEach workstation runs at most maxConcurrentShifts shifts at once (a runner config setting, default 4). The server caps it at AOM_MAX_SHIFTS_PER_WORKSTATION (default 16); a shift offered beyond the limit is rejected as busy and the card waits.Raise maxConcurrentShifts in the runner config (ceiling 16) and restart the runner, or pair another workstation.
Demo and E2E use a mock runtimeThe test suites and the demo do not run real agents; the mock adapter plays a script per card.Run real Claude Code on a workstation for real behavior (AOM_CLAUDE_SMOKE=1 runs a smoke test and spends tokens).

TOCMARK_s13x3_13.3 Things that look odd but are intended

Why card refs are not globally unique Card refs are the project key plus a number (e.g., WEB-1). Project keys are unique within one organization, so two users can each have a project WEB with a card WEB-1. A ref that matches cards in more than one of your projects is answered with 409 ambiguous_ref; the web app links by card ID.
Why the runner connects outbound, not inbound The runner on your workstation connects to the server over outbound WebSocket (WSS port 443) and stays connected. This eliminates firewall complexity (no inbound ports), keeps credentials and code on your machine, and works everywhere (VPN, office, home, mobile hotspot). The trade-off is that only one runner per workstation can be active; a second connection with the same token closes the first (the runner exits with code 3).
Why DevOps cannot be fired The DevOps engineer per workstation can only be reset (sandbox wiped), not fired. Every user gets one DevOps engineer on each workstation, which other agents and the manager ask directly; every request and action is logged on a thread. A reset wipes its sandbox the way a firing does.
Why card dependencies do not affect branching When a card depends on another, the dependent card must wait for the dependency to finalize before it claims the Build stage. However, it still branches from the working branch (main), not from the dependency's branch. This keeps branches simple and allows parallel builds once dependencies are done. Rebase conflicts are detected by the runner before the completion action.
Why decisions can only be answered by the owner (by default) Card decision policy defaults to owner_only so the card creator stays accountable for decisions on their work. On a shared project, the policy can be changed to any_manager to distribute decision authority. This is explicit: changing the policy is a deliberate choice, not an accident.
